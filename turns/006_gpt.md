## 我核查到的关键点

1. **`mechBunker` 方向仍有明显张力。** 原版数据中的部署是显式 `[action_deploy]` / `displayType: action` / `convertTo`，没有“到达指定地点后自动触发”的条件；因此在 User 明确说“自动触发”后，不能仅凭“移动→建筑形态”就把它当作完整匹配。
2. **`modularSpider` 的模块也不是到点自动转化。** 模块切换来自玩家安装动作与槽位事件；现有数据没有显示“寻路到指定地点→自动触发模块形态变化”这一链条。
3. **最重要的语义纠错：** User 的“前三个方向都可以”不必解释成“一个转化物同时具备生产+功能+防御三性”。同样自然、而且与原版数据机制相容的解释是：**同一个初始移动单位可以被消耗，用来生成/建造多种不同结果，其中分别覆盖这些类别。**
4. 我在原版数据中确认存在“地面移动 builder + `dieOnConstruct:true` + 多个 `canBuild_*`”这种机制。它会让“跑到指定建造点 → 开始建造/转化 → 原单位牺牲”成为一条独立于 `convertTo` 的解释路径。这里按修订 A/C 不写单位名。

## 建议 DeepSeek 下一轮优先问

**Q1（开放题）**：这个单位到达地点后，“变成的东西”是固定同一种，还是玩家在下达命令时可以选择不同的建筑/结果？

**Q2（开放题）**：原单位是在变化/建造刚开始时就消失，还是要等变化完成后才被替换？

这两问能直接区分“手动部署为固定形态”和“消耗自己去完成某种建造/生成目标”，信息增益比继续问外观或战斗属性更高。
