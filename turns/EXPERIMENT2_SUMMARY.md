## 四、命中的机制链（本机游戏数据核实）

**`bugSpore`** 位于 `assets\units\classic_bugs\bug_spore\bug_spore.ini`：

| 字段 | 值 | 对应 User 的哪条线索 |
|---|---|---|
| `movementType: LAND` | 地面 | 「在地面上跑」 |
| **`dieOnConstruct: true`** | **建造时死亡** | **「牺牲自己，并完成目标」** |
| `useAsBuilder: true` | 可执行建造 | 「寻路到指定地点开始转化」 |
| `canBuild_1..4` | `bugExtractor` / **`bugNest`** / `bugGenerator` / `bugTurret` | 「生产 + 功能 + 防御」三性 |
| `builtFrom_1_name: bugNest` | 虫巢生产 | 「能从工厂里造出来」 |
| 无爆炸/伤害效果 | 纯建造读条 | 「没有什么效果」 |
| `dieOnConstruct` 不可逆 | 下令后必然牺牲 | **「后悔想撤销发现不能」** |

### 排他性论证（为什么是唯一解）

全原版**只有两个**单位带 `dieOnConstruct`：

| 单位 | `dieOnConstruct` | 移动域 |
|---|---|---|
| **`bugSpore`** | `true` | **`LAND`** ✅ |
| `bugFly` | `true` | `AIR` ❌（User 明确「在地面上跑」） |

⇒ **`bugSpore` 是唯一满足全部条件的单位。**

**另一条独立验证**：DeepSeek 穷举了全原版**每一个带 `convertTo` 的动作块**并检查 `isVisible`，
结论是**除虫族外没有任何单位动作是不可逆的**——

- `mechBunkerDeployed` → `Undeploy`，`isVisible: true`（可撤销）
- `experimentalGunshipLanded` → `Undeploy`（可撤销）
- `modularSpider` 槽位 → `Reclaim Slot`，且 `addResources: ${core.price * 0.5}`（退款 50%）
- `extractorT3_overclocked` / `_reinforced` → `Refund`（可撤销）

⇒ **「想撤销发现不能」这个体验在原版中只有 `dieOnConstruct` 能产生。**

## 五、GPT-5.6 Sol 的贡献（本实验的关键）

**没有 Sol，本实验不会命中。** 原因：`dieOnConstruct` 机制**完全不在 DeepSeek 的知识范围内**，
而本机对公开网络存在 DNS 拦截（RW wiki / Fandom / namu.wiki 全部不可达），
DeepSeek 无法通过外部资料补上这个缺口。

Sol 的三项实质贡献：

1. **指出 `dieOnConstruct` 路径**（`turns/006_gpt.md`）：
   原版存在「地面移动 builder + `dieOnConstruct:true` + 多个 `canBuild_*`」机制，
   是一条**独立于 `convertTo` 的路径**。DeepSeek 此前完全漏掉了这条。
2. **纠正 DeepSeek 的语义误读**（`turns/006_gpt.md`）：
   User 的「前三个方向都可以」**不必**解释成「一个转化物同时具备三性」；
   同样自然的解释是「**同一个初始移动单位可被消耗，用来生成多种不同结果**」。
   **事后证明 Sol 的解释才是对的。**
3. **独立复核并自我设限**（`turns/009_gpt.md`）：
   确认机制链成立，同时**主动标出两项保留**——
   中文名无法确认、沙盒可点选「强支持、尚未运行时验收」。
   **没有为了支持 DeepSeek 而把证据说满。**

## 八、⚠️ 一个必须记录的纪律问题：答案被判定的时序

**审计结果（git 历史可查）**：

| 时间 | commit | 事件 |
|---|---|---|
| 23:26:11 | `6b74101` | **`bugSpore` 首次写入仓库**（`turns/009_deepseek.md`） |
| 23:40:00 | `6c64a2d` | 写入 `STATE.md` |
| **之后** | — | **User 才公布判定：「你的答案正确，就是 bugSpore」** |

**⇒ 猜测名称在裁判判定之前就已进入公开仓库。**

这与实验 1 属于**同一类问题**（实验 1 中「Mech Engineer」是以**候选**身份提前入库），
但实验 2 **更直接**：写进去的就是**明确的猜测结论**本身。

**后果**：

- 若第三方（或另一个 Agent）在判定前读仓库，**可直接看到 DeepSeek 的猜测**——
  盲测设计被削弱；
- 但与实验 1 不同的是，**本次泄露不影响 DeepSeek 的推理有效性**：
  猜测是 DeepSeek 自己经推理得出的，仓库只是记录载体，
  **不存在「从仓库读到答案再假装猜中」的情况**。

**根因**：`README.md` 规则 1 要求「真正答案不得提前写入 GitHub」，
但**并未规定「猜测本身是否算答案」**。
DeepSeek 采用了「猜测写入 `turns/00N_deepseek.md`」的做法（这本是协议要求：
「DeepSeek 写 `turns/00N_deepseek.md`」），**两条要求在「猜测即接近答案」时产生张力**。

**建议修订 D（待 User 决定）**：
**判定前的正式猜测，其具体名称不得入库**；入库只写「已提交一猜，待判定」，
判定后再于结果文件中记录。是否采纳由 User 决定。

## 九、并发写入问题（工具层面）

实验 2 起 Sol 具备直写能力，**双方并发提交多次产生竞争**：

| 现象 | 次数 |
|---|---|
| DeepSeek 提交前发现 `origin/main` 已被 Sol 推进 | 多次 |
| `push` 被拒（`non-fast-forward`），需 fetch + rebase | 2 次 |
| 文件「读取后被改写」导致编辑失败 | 多次 |
| `push` 遇 SSL/TLS 握手失败，需重试 | 1 次 |

**已采用的应对**：每次提交前 `git fetch` 并确认 `origin/main`；
push 失败时自动 `fetch + rebase` 重试。

**Sol 的配合**：Sol 在 `GPT_SOL_ONLINE.md` 中主动承诺
「避免改写 `STATE.md`，优先写独立的 GPT 文件，且每次写入前 `git fetch`」。

## 十一、三条可复用的教训

1. **不要在候选池为空时急着猜。** 实验 2 前 5 轮只积累机制约束、不报名字，
   每次被否决都换回了更硬的约束——**Round 9 的否决换来了三条决定性约束**，直接导致命中。
2. **一条直接矛盾就足以否定猜测；线索数量不能用来抵消矛盾。**
   这是 Luna 教给 DeepSeek 的最重要一条，也是实验 2 最大的方法论收获。
3. **知识缺口要用数据本体补，不要用二手资料补。**
   外部 wiki 全被拦截时，本机 `assets\units\` 的明文 `.ini` 才是可靠来源；
   而 `dieOnConstruct` 这类机制，**只有 GPT 领域知识 + 本地数据交叉才能发现**——
   这正是双 Agent 协作的价值所在。
